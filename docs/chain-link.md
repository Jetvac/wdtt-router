# Туннель цепочки

Статус: первый этап реализован (UDP и ICMP через туннель), ещё не выпущен и не проверен на настоящей цепочке. Ноябрь 2026.

Код: служба — `internal/link`, агент — `internal/agent/link.go` и правила в `internal/agent/wdtt.go`, панель — `internal/controller/link.go`, интерфейс — `web/src/components/ChainLink.tsx`.

## Коротко

Между входом и выходом появляется постоянный зашифрованный UDP-туннель на WireGuard. Он идёт **внутри Cloudflare Mesh**, как и сейчас идёт Xray. Через туннель идёт UDP- и ICMP-трафик клиентов WDTT и TurnVK. TCP остаётся на Xray. Если туннель перестаёт отвечать, UDP сам возвращается на Xray за 3–5 с.

- Для ТСПУ ничего не меняется. Вход по-прежнему говорит только с Cloudflare, адрес выхода в России не появляется. Блокировка адреса любого сервера на цепочку не влияет.
- Xray-цепочка остаётся: на ней TCP, 3x-ui и запасной путь для UDP.
- Клиентам обновляться не нужно, всё меняется только на серверах.
- Переход идёт в три шага: обновление панели (ничего не меняется) → режим «Проверка» (туннель поднят, клиентский трафик не идёт) → «UDP через туннель». Откат одним переключателем, мгновенно.

## Зачем: что показали данные

Статистика TurnVK за 23–26.11 (8 устройств) и проверка цепочки в панели:

| Участок | Сейчас |
| --- | --- |
| Клиент → VK → вход | ПК 7 мс (p95 17), телефоны 15–25 мс по Wi-Fi, 80 мс по плохому LTE |
| Новый TCP-запрос с входа через цепочку (панель: TCP) | 300 мс |
| DNS-запрос с входа через цепочку (панель: UDP) | 123 мс |
| Тест «Пинг» в клиенте | 7 мс, но это до входа: TCP принимает сам вход (TPROXY), цепочку тест не видит |

Как сейчас идёт UDP: каждый UDP-поток (DNS-запрос, соединение QUIC, звонок) Xray превращает в отдельное VLESS-подключение по TCP через Mesh. Это даёт три проблемы:

1. Первый пакет каждого потока ждёт установки TCP-подключения до выхода, это лишний круг по цепочке. DNS-запросы идут с разных портов, поэтому это ожидание повторяется на каждом запросе.
2. Потерянный в Mesh пакет задерживает весь поток, пока TCP его не перешлёт (обычно 200 мс и больше). Звонок или игра на это время замирают целиком, хотя могли бы просто потерять один пакет.
3. QUIC (YouTube, Google, Instagram) работает внутри TCP: его управление скоростью не видит настоящих потерь и задержек.

По цифрам панели один круг вход ↔ выход по Mesh оценивается в 50–60 мс. Точное значение покажет режим «Проверка».

## Что не меняется

- **Mesh как транспорт.** Туннель идёт между Mesh-адресами серверов (100.96.x) через `CloudflareWARP`, снаружи видно то же, что сейчас: MASQUE до Cloudflare.
- **Сокрытие от Cloudflare.** Cloudflare и промежуточные серверы видят только шифротекст. Расшифровать трафик клиента может только выход.
- **Xray-цепочка.** Конфигурация и работа те же. Когда туннель выключен, файлы, правила и службы побайтно совпадают с нынешними; это проверяется тестом.
- **Kill switch.** Трафик клиентов выходит только через туннель или через Xray, никогда с адреса входа.
- **Клиенты** WDTT и TurnVK. Протокол клиент ↔ вход не меняется.

## Устройство

```text
Клиент ─▶ wdtt0/wdtt1 ─┬─ TCP ────────▶ TPROXY ─▶ Xray ─▶ VLESS по Mesh ─▶ выход ─▶ Интернет   (как сейчас)
                       └─ UDP, ICMP ──▶ wrlink0 ─▶ WireGuard по Mesh (UDP) ─▶ wrlink0 выхода ─▶ NAT ─▶ Интернет
```

### Вход

- Служба `wdtt-router-link` (`wdtt-router link --config /etc/wdtt-router/link.json`) держит интерфейс `wrlink0` (10.66.80.1/30) и туннель до выхода.
- nftables (таблица WDTT, которая уже есть):
  - набор `via_link` (интерфейсы WDTT, `flags timeout`). Пока интерфейс в наборе, его UDP и ICMP не уходят в TPROXY, а маршрутизируются в туннель. Пока его нет в наборе, всё идёт в Xray, как сейчас;
  - forward: из `wdtt*` пропускается только в `wrlink0` (UDP, ICMP) и обратно по `ct state established,related`, всё остальное сбрасывается, как сейчас;
  - SNAT в `wrlink0` на 10.66.80.1: выход не знает адресов клиентов.
- Маршрутизация: правило `iif wdtt* lookup 51889` (приоритет 10667) после правила TPROXY (10666) и `fwmark 0x2 lookup 51889` (10668) для собственных проверок входа. В таблице два маршрута: `default dev wrlink0` и `blackhole default` с большей метрикой. Пока интерфейса нет (служба перезапускается), пакет тихо отбрасывается и не уходит в основную таблицу.
- Пересылка включается только на нужных интерфейсах (`net.ipv4.conf.<iface>.forwarding`): `wdtt0`, `wdtt1`, `wrlink0`. Глобальный `ip_forward` и публичный интерфейс не трогаются, сервер не становится маршрутизатором для соседей.

### Выход

- Та же служба отвечает на рукопожатие входа на `<Mesh-адрес>:<порт туннеля>`.
- Ограничения те же, что у Xray-выхода: запрещены частные сети, Mesh-диапазоны и TCP-порт 25. Пересылка идёт только из `wrlink0` в публичный интерфейс и обратно по `established,related`, остальная пересылка с публичного интерфейса сбрасывается.
- Masquerade в публичный интерфейс, поэтому адрес выхода в Интернете тот же, что у Xray.
- Firewall: порт туннеля по UDP открыт только из 100.96.0.0/12 на `CloudflareWARP`, как сейчас TCP-порт звена.

### Промежуточный сервер

Та же служба в роли `relay` пересылает датаграммы туннеля на следующий Mesh-адрес, не читая их, и ключей не имеет. Пересылка идёт в пространстве пользователя, а не через NAT ядра: так серверу не нужна пересылка пакетов на `CloudflareWARP`, которую клиент Cloudflare сбрасывал бы при каждом переподключении. Сервер по-прежнему знает только следующее звено и видит только шифротекст. Вход направляет туннель на первый промежуточный сервер, выход видит Mesh-адрес последнего, как сейчас.

### Протокол туннеля

Основа — **wireguard-go** с собственным транспортом (`conn.Bind`). Такая связка уже работает в сервере WDTT и в клиенте TurnVK. Берём проверенное: рукопожатие Noise IK, X25519, ChaCha20-Poly1305, смену ключей каждые 2 минуты, защиту от повторов и смену адреса собеседника на лету (roaming). Свой транспорт добавляет к этому три вещи:

1. **Постквантовая защита.** Сейчас VLESS Encryption использует ML-KEM-768 + X25519. Туннель получает общий ключ (PSK, 32 случайных байта на звено). Его создаёт панель, по сети он не передаётся. Записанный сегодня трафик нельзя будет расшифровать и будущим квантовым компьютером.
2. **Маскировка.** Каждый датаграм начинается с 8 случайных байтов. Заголовки WireGuard и рукопожатия закрыты потоком ChaCha20 из ключа звена. Cloudflare видит случайные байты, как сейчас с `random`-режимом VLESS.
3. **Своя нарезка пакетов.** Размер пакета в Mesh не фиксирован: по умолчанию 1280, но клиент Cloudflare понижает его по Path MTU Discovery, вплоть до 1147–1199 байт ([журнал изменений](https://developers.cloudflare.com/cloudflare-one/changelog/warp/), [PMTUD](https://developers.cloudflare.com/cloudflare-one/team-and-resources/devices/cloudflare-one-client/deployment/mdm-deployment/path-mtu-discovery/)). Клиенты шлют пакеты до 1280 байт (до 1340 по настройке), а QUIC требует не меньше 1228. Поэтому туннель сам режет большие пакеты на 2 части и собирает их на другой стороне. На IP-фрагментацию внутри Cloudflare он не рассчитывает: проходят ли фрагменты через прокси Gateway, неизвестно. Размер части следует за MTU `CloudflareWARP` (читается каждые несколько секунд) и подтверждается пробными пакетами.

| MTU Mesh | Место под датаграм | Пакет клиента целиком | Режется на 2 части |
| --- | --- | --- | --- |
| 1280 | 1252 | до 1200 | 1201–1340 (большие QUIC) |
| 1199 | 1171 | до 1120 | 1121–1340 |
| 1147 | 1119 | до 1072 | 1073–1340 |

Издержки на пакет: 8 байт маскировки, 4 байта нарезки, 32 байта WireGuard и выравнивание до 16 байт. Сборка частей ограничена по памяти (не больше 256 незавершённых пакетов) и по времени (200 мс). Потеря одной части теряет пакет целиком, так же как при IP-фрагментации.

**Пробы.** Каждые 0,5 с туннель шлёт короткий пинг (около 50 байт, с кодом проверки HMAC). По ответам он знает круг, потери и живость пути. Пробный пакет полного размера уходит при старте, при смене MTU `CloudflareWARP` и раз в 10 минут; если три подряд теряются, а обычные пинги доходят, датаграммы уменьшаются на 64 байта, и раз в 10 минут туннель пробует полный размер снова. Пинги держат открытой UDP-сессию в прокси Cloudflare, поэтому её таймаут простоя не важен.

**Перезапуск выхода.** В ответе на пинг выход сообщает номер своего запуска. Если служба выхода перезапустилась, у её WireGuard больше нет ключей, и пакеты входа молча отбрасывались бы, пока WireGuard входа сам не сдастся (около 15 с). Вход видит новый номер и сразу начинает новое рукопожатие: трафик возвращается за долю секунды.

**Проверка насквозь.** Каждые 15 с вход спрашивает DNS у 1.1.1.1 или 9.9.9.9 через туннель (меткой 0x2). Так проверяется не только канал, но и пересылка с NAT на выходе.

### Переключение и «мёртвая рука»

Решение о пути принимает служба туннеля на входе. Сам выбор хранит ядро:

- Пока туннель здоров, служба каждую секунду добавляет интерфейсы WDTT в `via_link` с таймаутом 5 с.
- Если служба упала, зависла или остановлена, ядро само удаляет запись через 5 с, и UDP уходит в Xray. Для отката никакая программа не нужна.
- «Здоров» значит: на пинги есть ответы, рукопожатие WireGuard моложе 3 минут (без него не больше 15 с после старта) и DNS через туннель не отказал 3 раза подряд. 3 с без единого ответа (6 пингов подряд) — переключение на Xray, но только если Mesh до следующего сервера при этом работает: после 1,5 с тишины вход пробует TCP-рукопожатие с его Xray по Mesh (отказ в подключении тоже считается ответом). Если и оно не проходит, пропал сам Mesh, по которому идёт и Xray: переключение ничего бы не дало и дважды порвало бы потоки UDP, поэтому UDP ждёт в туннеле до 30 с, а пережитый обрыв попадает в журнал панели и в карточку. Обрывы Mesh до 3 с туннель пережидает всегда, не разрывая потоки.
- Возврат на туннель — после 30 с без проблем. Пока UDP клиентов на Xray, «без проблем» строже: DNS через туннель уже ответил в этом запуске и последняя проверка прошла. Иначе UDP переходил бы на туннель с двумя отказами DNS и через несколько секунд возвращался (так тест в CI нашёл это).
- Против «дребезга»: после 3 переключений за 15 минут туннель остаётся на Xray ещё 15 минут, панель и бот сообщают об этом.
- Перезапуск службы (обновление панели) укладывается в 5 с: остановленная служба запись не убирает, а новая, найдя её, продолжает обновлять, пока заново проходит рукопожатие. Потоки не переключаются.
- Смена режима «Проверка» ↔ «UDP» не перезапускает службу: агент шлёт ей SIGHUP, и она перечитывает режим. Выключение туннеля убирает правила целиком, и UDP сразу возвращается в Xray.
- Применение настроек агентом и обслуживание раз в 30 с никогда не очищают `via_link`. Скрипт nftables при включённом туннеле пересоздаёт цепочки, а не всю таблицу. Правило маршрутизации и флаги пересылки восстанавливаются так же, как сейчас правило TPROXY: `systemd-networkd` иногда удаляет чужие правила.

## Устойчивость: что будет, если…

| Событие | Сейчас (Xray) | С туннелем (UDP) |
| --- | --- | --- |
| Mesh пропал на 1–3 с | TCP-подключения между серверами замирают, при разрыве рвутся все подключения клиентов | пакеты за эти секунды теряются, потоки продолжаются |
| Mesh пропал на 3–30 с | то же | UDP ждёт в туннеле (Xray без Mesh тоже стоит), потоки продолжаются; в журнале — «Mesh пропадал на N с: туннель переждал» |
| Mesh пропал дольше | у клиентов нет Интернета | через 30 с UDP переходит на Xray, но и он без Mesh не работает, итог как сейчас; возврат автоматический |
| Туннель молчит, а Mesh работает | — | через 3 с UDP на Xray; в причине — «хотя Mesh до следующего сервера работает» |
| Cloudflare понизил MTU (1147–1280) | TCP подстраивается | размер частей следует за MTU, пробы подтверждают |
| Прокси Cloudflare сменил UDP-порт сессии | — | WireGuard принимает новый адрес собеседника на лету |
| Перезапуск или сбой службы на выходе | — | вход видит новый запуск по ответу на пинг и сразу делает новое рукопожатие (доли секунды); если выход молчит дольше 3 с, UDP на Xray |
| Сбой службы на входе | — | через 5 с ядро само переводит UDP на Xray; systemd перезапускает службу за 1 с |
| Обновление панели | Xray перезапускается при обновлении версии | службы туннеля перезапускаются в пределах 5 с, без переключения |
| Потери в Mesh | превращаются в задержки всего потока (TCP) | теряется один пакет, приложение (QUIC, звонок) справляется само |
| Туннель «дребезжит» | — | после 3 переключений за 15 мин 15 мин на Xray и уведомление |
| Не работают оба пути | нет Интернета (kill switch) | так же |
| На выходе Docker или ufw (iptables FORWARD отбрасывает пересылаемое) | — | агент добавляет в FORWARD два разрешения для туннеля и проверяет их раз в 30 с: Docker и ufw переписывают цепочку при перезапуске |
| На сервере строгая проверка обратного пути (rp_filter = 1) | — | служба делает её на `wrlink0` нестрогой: ответы из Интернета приходят через туннель, а основной маршрут к ним идёт мимо |

Переключение пути (туннель ↔ Xray) один раз обрывает идущие UDP-потоки: у них меняется исходный порт на выходе. QUIC и звонки переподключаются сами за доли секунды – секунды, TCP это не затрагивает.

## Безопасность

- **Cloudflare** видит один долгий UDP-поток случайных байтов между двумя Mesh-адресами. Сейчас он видит отдельное TCP-подключение на каждое подключение клиента, с его временем и объёмом, так что туннель раскрывает меньше.
- **Промежуточный сервер** пересылает шифротекст по одному адресу и ключей не имеет.
- **Выход** знает открытый ключ туннеля входа и видит Mesh-адрес предыдущего звена, как сейчас. Адреса клиентов скрыты за SNAT входа.
- **Ключи** (закрытые ключи входа и выхода и PSK, из которого выводятся ключи маскировки и проверки пингов) хранятся в базе панели зашифрованными, как ключи звеньев. Каждый сервер получает только своё. Новый выход получает новые ключи и PSK; кнопки «Перевыпустить ключи» пока нет.
- **Выход** не пускает трафик в частные сети, Mesh и на порт 25, как Xray-выход сейчас.
- **Пересылка** включается на отдельных интерфейсах, а не на всём сервере. Пересылку с публичного интерфейса правила разрешают только для ответов (`established,related`) в туннель.

## Переход на работающем сервере

0. **Обновление панели.** Без изменений: туннель выключен, конфигурация побайтно прежняя.
1. **Режим «Проверка»** (карточка «Туннель цепочки» на обзоре и на странице цепочки). Панель создаёт ключи, сначала применяет выход, потом вход, как сейчас звенья. Туннель поднимается рядом с Xray, клиентский трафик через него не идёт. Панель показывает круг, потери, MTU, проверку больших пакетов, DNS и скорость через туннель рядом с цифрами Xray. Достаточно оставить так на несколько часов или на сутки.
2. **«UDP через туннель».** Включается мгновенно, без перезапусков. Панель предупредит, что текущие звонки и QUIC-соединения один раз переподключатся. Переключатель не включится, пока проверка не пройдена.
3. **Откат** — «Xray» в той же карточке: UDP возвращается на Xray сразу, туннель останавливается.

Режим можно включить, только когда все серверы цепочки обновлены до версии с туннелем: панель смотрит, что сообщают их агенты. Вход и выход обновляются вместе с панелью, как сейчас.

## Что проверяет режим «Проверка»

Вещи, которые нельзя знать заранее и от которых зависит устойчивость. Часть из них — условие, без которого панель не даст включить «UDP через туннель», часть видна в карточке, и решение за администратором.

| Вопрос | Как проверяется | Условие для «UDP через туннель» |
| --- | --- | --- |
| Проходит ли UDP между узлами Mesh (Gateway UDP proxy) | рукопожатие WireGuard и пинги | есть ответы, рукопожатие свежее |
| Пересылка и NAT на выходе | DNS к 1.1.1.1 и 9.9.9.9 через туннель каждые 15 с | DNS ответил |
| Настоящий MTU Mesh и его изменения | MTU `CloudflareWARP` и пробные пакеты полного размера | пакет полного размера прошёл |
| Потери и задержка UDP по Mesh | пинги каждые 0,5 с: круг (медиана и 95 %) и потери за минуту, график круга | видно в карточке |
| Скорость и нагрузка на `warp-svc` | загрузка 10 МБ с `speed.cloudflare.com` через туннель и через Xray по кнопке «Проверить» | видно в карточке |
| На чём работает WARP входа: HTTP/3 (QUIC) или запасной HTTP/2 (TCP) | пока вручную: `ss -tunp \| grep warp` на входе | при HTTP/2 пропадает выигрыш по потерям, остальной остаётся |

## Что покажет панель

- Карточка «Туннель цепочки» на обзоре и на странице цепочки: режим, состояние, путь UDP клиентов и последнее переключение с причиной, круг и потери, пережитые обрывы Mesh, размер пакетов, DNS через туннель, рукопожатия входа и выхода, трафик, пакеты через туннель на обоих концах (туда и обратно), интерфейс выхода в Интернет и что понадобилось для iptables, а если ядро или межсетевой экран сервера отбросили бы пакеты туннеля — где именно. Пока проверка не прошла, панель называет место, где пакеты останавливаются. Последняя проверка — таблица «Xray / Туннель»: DNS, новый запрос HTTPS, скорость.
- Уведомления бота и журнал событий: «UDP клиентов переключён на Xray: …», «UDP клиентов снова идёт через туннель цепочки»; строка туннеля в `/status`.
- На графике «Задержка цепочки» — круг по туннелю рядом с временем нового запроса через Xray.

## Задел на следующие шаги

1. **DNS-кэш на входе.** Клиенты получают DNS-адрес входа (10.66.67.1), кэш спрашивает 1.1.1.1 через туннель. Повторный запрос стоит 7–25 мс (круг до входа) вместо круга по цепочке. Метка 0x2 для собственного трафика входа через туннель уже есть, кэш будет пользоваться ею.
2. **TCP через туннель**, только по результатам сравнения. Сейчас TCP клиента заканчивается на входе, и потерю на участке клиент ↔ вход (0,3–1,4 % у телефонов) вход перепосылает за 7–80 мс. Через туннель её перепосылал бы сайт за полный круг. Поэтому TCP переводится только после того, как сравнение (время первого байта, скорость на телефонах с потерями) покажет выигрыш. Это будет третий режим, «Всё через туннель», с ограничением размера сегментов TCP под туннель.
3. **Несколько выходов.** Второй выход в режиме «Проверка» рядом с первым: сравнение кругов и переход на него при отказе первого. Выход ближе к Москве (Хельсинки, Стокгольм, Варшава) убавит 15–25 мс от каждого пакета.
4. **Измерение в клиенте TurnVK.** Через туннель проходит ICMP, и клиент сможет мерить полный путь до Интернета (DNS-запрос или пинг через туннель), а не только до входа.
5. **HTTP/3 или HTTP/2 у WARP** — показывать в карточке, а не проверять вручную.

## Тесты

- `internal/link`: нарезка и сборка (перестановка, повторы, мусор, устаревшие части, предел памяти); маскировка и HMAC пингов; решение о пути (возврат через 30 с, обрывы до 3 с, «дребезг», перезапуск с подхватом, рукопожатие, DNS); два настоящих устройства wireguard-go через имитацию Mesh: пакеты до 1340 байт при MTU 1147, 3 % потерь, смена порта прокси, поиск меньшего пути и возврат к полному, переход на Xray и обратно, промежуточный сервер, перезапуск выхода (трафик снова идёт за 0,2 с; без номера запуска — больше 5 с).
- `internal/agent`: правила входа без туннеля побайтно совпадают с прежними; правила с туннелем, выхода, firewall, конфигурация службы для каждой роли, перезагрузка только режима.
- `internal/controller`: план с туннелем (ключи парные и не меняются между планами, старые агенты туннеля не получают), MTU туннеля, условия готовности, уведомления о переключениях.
- CI, сетевые пространства имён (`TestNetnsLink`, от root): настоящая служба и правила агента. Клиент за `wdtt1`, вход и выход, «Mesh» из veth (задержка 20 мс и 1 % потерь, если ядро даёт netem), «Интернет» с эхо и DNS. Проверяется: UDP до 1280 байт и ping через туннель; MTU Mesh 1147; перезапуск службы входа без переключения; обрыв Mesh — UDP уходит с туннеля и возвращается; служба убита — ядро само снимает туннель; на выходе iptables FORWARD с политикой DROP (как у Docker и ufw), на обоих концах строгий rp_filter; обе стороны видят свободный путь и считают пакеты; ни в одном случае трафик клиента не выходит с адреса входа.
- Настоящий Cloudflare Mesh проверяется режимом «Проверка» на рабочей цепочке, без клиентского трафика. Первая проверка (1.6.0, 26 ноября) нашла то, чего нет в тестах: Docker на выходе с политикой DROP в iptables FORWARD. Пробы, рукопожатия и пакеты до 1272 байт проходили, а пересылаемые в Интернет пакеты отбрасывались. Это исправлено в 1.6.1 и добавлено в тест.
