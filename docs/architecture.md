# Архитектура

Контроллер `wdtt-panel` запускается на входном VPS и хранит SQLite в `/var/lib/wdtt-panel`. Веб-интерфейс встроен в бинарный файл. Управляемые узлы используют тот же бинарный файл как локальный агент, вызываемый контроллером по SSH. Постоянного обратного соединения от агента нет.

| Часть | Назначение |
| --- | --- |
| `internal/controller` | HTTPS API, очередь заданий, Cloudflare API, встроенный интерфейс |
| `internal/auth` | Argon2id, сессии и CSRF |
| `internal/store` | SQLite, миграции, шифрование секретов AES-GCM, очистка журнала |
| `internal/transport` | SSH bootstrap, отпечатки ключей, запуск агента |
| `internal/node` | WDTT, Mesh, маршруты, firewall, 3x-ui, VLESS, самопроверка и откат |
| `cmd/wdtt-panel` | CLI контроллера и агента |

Задание записывается в базу с зашифрованным входом. Один worker берёт его из очереди, применяет на нужном узле, проверяет новую связь, подтверждает или инициирует откат. Для сетевых действий узел до изменения запускает отдельный systemd timer на 180 секунд. Поэтому потеря связи с контроллером не отменяет восстановление.

Cloudflare-профиль, узлы и маршруты создаются только после проверки аккаунта и пересечений. База хранит ID каждого ресурса с меткой `created` или `imported`; удаление чужих ресурсов запрещено. Дополнительный список запрещённых аккаунтов читается из `/etc/wdtt-panel/protected-accounts` на контроллере.

На каждом узле конфигурация Mesh находится в `/etc/wdtt-panel/mesh.json`, маршруты в `routing.json`, правила firewall в `firewall.json`, а VLESS в отдельных файлах того же каталога с правами root. Службы systemd восстанавливают собственные правила после перезагрузки.

Панель 3x-ui на обоих VPS привязана к loopback. Её приватный VLESS вход доступен только через Mesh. Отдельный Xray на входном VPS перехватывает только пакеты подсети WDTT с интерфейса `wdtt0`, а не исходящий трафик самого хоста.
